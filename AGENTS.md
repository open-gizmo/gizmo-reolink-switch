# Agent instructions

For AI agents (Claude Code, Codex, Copilot and others) working on this repository. `CLAUDE.md` imports this file, so every agent reads the same rules.

## What this project is

Gizmo Reolink Switch lets you leave home without triggering your own cameras: a button on a Seeed Studio XIAO ESP32-S3 mutes the notifications and recording of a Reolink NVR for a while, then turns them back on. A 16x2 LCD and a buzzer give feedback, and a web app built into the firmware sets it up from the phone and shows its status.

- `microcontroller/` is the PlatformIO firmware: the button, the timer, the LCD and buzzer, the Reolink API calls, and the web app and its API.
- `webapp/` is the Nuxt 4 web app, embedded in the firmware: the Switch page (the status), the NVR login, the device card and the Wi-Fi setup. It extends the [gizmo-common](https://github.com/open-gizmo/gizmo-common) web layer, and the mock switch in `webapp/server/` answers like the firmware during development.

## Structure

- `src/main.cpp`: the entry point; shows the setup steps, polls the button, runs the timer and keeps the LCD and buzzer in sync.
- `src/button`, `src/buzzer`, `src/display`: the button events, the sounds and the LCD screens.
- `src/menu`: the timer selection and countdown.
- `src/reolink`: logs in to the NVR and turns notifications and recording off and on.
- `src/channels` and `src/storage`: which setting is muted on which channel, saved in NVS so a reboot can't leave the cameras muted.
- `src/nvr`: the NVR login set from the web app, saved in NVS.
- `src/remote`: hands the web app's NVR check to the main loop, and publishes the switch's state for the web app.
- `src/server`: the web app and its API, one file per endpoint (the Wi-Fi setup and device routes come from gizmo-common).
- `src/wifi`, `src/config`, `src/serial`: the Wi-Fi setup names, the pins and timings, and the serial log.
- `src/webui`: generated by `npm run build:embedded`, never edited by hand.

## Working rules

1. **Never delete comments that are already in the code.**
2. The quiet mode is controlled from the button only, on purpose: the web app sets the switch up and shows its status, but never starts, cancels or retries the quiet mode, and no endpoint controls the cameras.
3. Only the main loop talks to the NVR: the web server hands requests over through `src/remote`.
4. The NVR password is write-only: the API never sends it back, and changing the NVR's address or username clears it.
5. When a route, payload or validation rule changes, update the firmware handlers, the mock switch in `webapp/server/` and the web app together, and translate every new error ID.
6. Keep hardware-free logic free of hardware headers, and test it with `pio test -e native`.
7. Prefer small, hardware-aware changes: no blocking calls, no needless allocations, no broad refactors unless they are needed.

## With every change

1. **Write the changelog.** When a maker would notice the change (a feature, the web app, the hardware or wiring, the setup steps, a fix), add a line under `## Unreleased` in [CHANGELOG.md](CHANGELOG.md), in the same commit. Write it for the people who flash and use the gadget, not as a commit message: what changed for them, and what they need to do (flash again, rewire, set something up again). Internal changes (refactoring, tests, CI) need no line unless they change what the gadget does.
2. **Keep the docs in sync.** Update the README (and its screenshots in `docs/` when the web app looks different), and tell the user when the gadget's page on [opengizmo.dev](https://opengizmo.dev) needs the same change.
3. **Check it before calling it done.** Run the tests (`pio test -e native` in `microcontroller/`, `npm test` in `webapp/`) and the release build (`npm run build:embedded` in `webapp/`, then `pio run -e release`).

## Releasing

Follow "Releasing a new version" in the README. The version's notes must be moved from `## Unreleased` to a `## vX.Y.Z - YYYY-MM-DD` heading in CHANGELOG.md: they become the GitHub release notes, and the release workflow stops before building anything when they are missing or when notes are left under Unreleased.

Every OpenGizmo gadget has its own release workflow file, and they are kept the same apart from the gadget's name and module (chip), which sit in the `env` block at the top. When you change one, make the same change in the others.

Work on the `feature` branch; changes reach `develop` and then `main` one step at a time, only for a release.
